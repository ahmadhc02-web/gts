I have completed the collaborative editing feature for the Recovery Rows table. It works identically to Google Sheets live cursors. Here is how it was implemented:

- **Presence Channel**: Implemented a Supabase Realtime channel scoped to the active month (`billing-presence-{monthId}`). Users automatically join this channel upon viewing the sheet, publishing their user ID and name.
- **Visual Cursor Indicators**: Added a global focusin/focusout event listener that translates DOM focus changes into broadcast payloads (`action: 'focus' | 'blur'`). These are broadcasted to other clients listening in the channel. When another user receives the cursor-move broadcast, a distinct, colored highlight border and an absolute positioned name tag dynamically render around the exact cell being edited. Colors are derived via a hash function from the user's ID for consistency.
- **Graceful Disconnect Cleanup**: In addition to tracking `blur` actions, the `presenceState` sync is monitored so that if a user disconnects or closes their tab unexpectedly, any stale cursors belonging to them are instantly cleared from the view.
- **Throttling & Overflow Overrides**: Broadcasts are restricted strictly to field focus and blur events rather than individual keypresses, keeping latency low without flooding the connection. I also removed `overflow-hidden` classes from the table cell markup, allowing the absolute-positioned collaborative name-tags to bleed over cell boundaries perfectly without getting clipped.
- **Data Sync Reliability**: The actual data mutations safely leverage the existing `postgres_changes` listener on `billing_months`. When a user's edits are batched and saved to Supabase (utilizing the new deduplication logic), the server payload inherently arrives to other connected clients via realtime, mapping cleanly onto the view.
